# FEATURE_ENFORCEMENT_MATRIX.md

For every fork-relevant behavior: which layer actually enforces it, and — critically — which layers do **not**. A feature can be "enforced" at several layers at once; the interesting cases are the ones enforced at *fewer* layers than a reader might assume from the product description alone. Used as an upgrade-verification artifact by `docs/FORK_AUTOMATION.md` and `docs/UPSTREAM_UPGRADE_GUIDE.md` — re-check every "Yes" cell against the cited source after any upstream version bump.

## Enforcement layer definitions

- **UI enforced** — a control is shown/hidden in the Dart UI. A custom or unmodified upstream client bypassing this fork's UI entirely is *not* affected.
- **Config enforced** — `src/fork_config.rs` reads a `direct-ip-*` option from `RustDesk2.toml` and acts on it (sets an upstream option, a `HARD_SETTINGS` entry, etc.). Says nothing on its own about whether the *effect* is a hard protocol-level block or just a local preference.
- **Remotely enforced** — the *receiving* side rejects the action at the protocol/login level, regardless of what client software initiates it. This is the one that actually matters for security/product guarantees — "remotely enforced: No" means a stock RustDesk client (or any client speaking the protocol) can still do the thing even if this fork's own UI would never offer it.
- **Upstream enforced** — the actual enforcement code is pre-existing, unmodified RustDesk code; the fork only feeds it a value. (Almost everything in this fork is upstream-enforced by design — see `docs/architecture.md`'s "no redesign" decisions. Marked "No" only where the fork introduces something with no direct upstream equivalent, e.g. the `desktop-share-enabled` option itself.)

## Current status: `support_enabled` vs. `desktop_share_enabled`

These two flags look symmetric in configuration (`docs/architecture.md`'s schema, `docs/FORK_PROFILE_SPEC.md`) but are **not** symmetric in enforcement:

- **`support_enabled` is enforced at all four layers** — UI, config, remote, and upstream. Disabling it via `direct-ip-support-enabled` in `RustDesk2.toml` on the remote/host machine makes `VIEW_CAMERA` (and therefore Voice Call, which rides on it) genuinely unreachable, for any client, because it reuses the existing upstream `enable-camera` login-time permission check (`src/server/connection.rs:2544-2551`). This was a deliberate reuse of an existing upstream mechanism, not new code — see `src/fork_config.rs::apply()`.
- **`desktop_share_enabled` provides UI-level restriction only.** It is loaded and validated by the fork's config layer, and the Desktop button is genuinely hidden client-side (`connection_page.dart`) — but there is **no remote-side enforcement**. No upstream permission exists that rejects a `DEFAULT_CONN` login outright the way `enable-camera` does for `VIEW_CAMERA` (confirmed in `docs/session-orchestration-analysis.md` §2: `DEFAULT_CONN`'s video is unconditional once accepted; `try_sub_monitor_services()` calls `try_add_primay_video_service()` with no permission gate at all). Adding such a gate would mean writing a new authentication-path check in `src/server/connection.rs`'s login handler — explicitly out of scope without conclusive proof of necessity (per this project's standing constraints), and not something this phase implemented. **Practical consequence:** on a host with `desktop_share_enabled = false`, anyone who can authenticate (per `authentication.mode`) can still open a full remote-desktop-control session using this fork's own binary with a hand-crafted request, a stock RustDesk client, or any other client speaking the protocol — the flag only removes the button from this fork's own UI. This was investigated and documented as a known gap (`docs/FORK_PROFILE_SPEC.md`'s Configuration Profile), not silently implemented or silently left undocumented.
